# 팀 기능 전달 파이프라인

이 문서는 진단 증상 표시 개선과 반려동물 궁합·추천·MBTI 기능을 팀원이 같은 기준으로 이어서 구현하기 위한 작업 계약입니다.

## 공통 원칙

- 기능 작업은 `Backend` 최신 커밋에서 분기하고, 완료할 때마다 한글 `CHANGELOG.md`와 한글 커밋 메시지를 포함해 `origin/Backend`에 푸시합니다.
- `.env`, `backend/.env`, `local.properties`, 카카오 키, JWT 비밀값, 데이터베이스 비밀번호는 절대 커밋하지 않습니다.
- 서비스 결과는 의료 진단이나 입양 보장을 의미하지 않는다는 안내를 표시합니다.
- 작업자는 아래 인수 조건을 충족하기 전 다음 단계 또는 배포 단계로 넘기지 않습니다.

## 1. 진단 증상 표기 개선 (우선순위 P1)

### 문제

현재 지식그래프의 `rdfs:label` 전체가 Android Chip 하나로 표시됩니다. 예를 들어 `구토, 역류`는 그래프의 단일 ID지만, 화면에서는 서로 다른 증상을 한 번에 선택하는 것처럼 보입니다.

### 금지 사항

- 쉼표만 기준으로 Chip을 기계적으로 분리하지 않습니다.
- 같은 지식그래프 ID를 여러 Chip에 연결하지 않습니다. 중복 선택과 추론 점수 왜곡이 발생합니다.
- 수의 검토 없이 `구토`와 `역류`처럼 임상적으로 구분 가능한 징후를 동의어로 확정하지 않습니다.

### 구현 계약

1. 원본 TTL의 ID와 원문 라벨은 출처 보존용으로 유지합니다.
2. 정규화 매핑에 `displayName`, `aliases`, `relatedSigns`, `reviewStatus`를 추가합니다.
3. `/symptoms` 응답은 대표 표시명과 보조 표현을 제공하고, `/diagnosis/infer`에는 대표 ID만 전달합니다.
4. Android는 대표명만 Chip에 표시하고, 동의어는 보조 문구 또는 상세 보기로 노출합니다.
5. 임상적으로 독립된 징후는 수의 검토가 끝난 뒤에만 별도 ID·별도 질병 연결로 분리합니다.

### 인수 조건

- `식욕부진, 식욕감소, 식욕절폐`는 대표명과 원문 표현이 모두 확인된다.
- `구토`와 `역류`는 동의어 확정 전까지 독립 선택지로 가장하지 않는다.
- 기존 증상 ID를 이용한 진단 API 회귀 테스트가 통과한다.
- Android에서 동일 ID가 중복 선택되지 않는다.

## 2. 궁합·맞춤 반려동물·MBTI (지식그래프 비사용)

세 기능은 질병 지식그래프와 분리합니다. 신규 지식그래프를 만들지 않고, 사용자 설문 응답·기존 구조동물/시설 데이터·검증된 공개 데이터만 이용합니다.

| 기능 | 입력 | 결과 | 구현 원칙 |
| --- | --- | --- | --- |
| 반려동물 궁합 테스트 | 생활 패턴, 활동량, 주거 환경, 반려 경험 | 적합도와 근거 | 재미·참고용 결과이며 입양 추천 보장이 아님 |
| 나에게 맞는 반려동물 찾기 | 궁합 설문 + 기존 구조동물 필터 | 조건에 맞는 구조동물 목록 | 점수 기준과 제외 사유를 결과에 표시 |
| 반려동물 MBTI | 보호자가 응답한 행동 성향 설문 | 성향 유형과 돌봄 팁 | 의료·행동 진단으로 표현하지 않음 |

### 데이터 소스 방침

- 1차: 저장소의 기존 구조동물·시설 공공데이터와 사용자의 설문 응답을 사용합니다.
- 선택 보강: 개 품종의 공개 정보가 필요할 때만 MIT 라이선스 오픈소스 [dogapi.dog](https://github.com/kinduff/dogapi.dog)를 어댑터 뒤에서 조회합니다. 서비스가 중단되어도 핵심 추천은 기존 데이터와 설문 점수로 동작해야 합니다.
- 외부 API의 키·약관·라이선스가 확인되지 않은 데이터는 제품 데이터베이스에 복제하거나 재배포하지 않습니다.
- 고양이 품종 성향처럼 라이선스와 근거가 확정되지 않은 데이터는 추정하지 않으며, 공통 설문·구조동물 메타데이터 기반 결과만 제공합니다.

### 추천 점수의 최소 명세

각 문항은 `activity`, `space`, `time`, `experience`, `size`, `noiseTolerance` 중 하나에 점수를 부여합니다. 후보 동물도 같은 차원으로 정규화하고, 일치·불일치 항목을 함께 반환합니다. 최종 결과에는 총점만이 아니라 “왜 추천/제외됐는지”를 표시합니다.

## 3. 작업 순서와 담당 인수

1. **기획/데이터 담당**: 질문지, 점수표, 문구, 데이터 출처·라이선스 표를 작성하고 승인받습니다.
2. **백엔드 담당**: 입력/출력 스키마, 점수 계산기, 필터 API, 단위 테스트를 구현합니다.
3. **Android 담당**: 설문 화면, 결과 근거, 빈 상태·오류 상태, 접근 가능한 문구를 구현합니다.
4. **검증 담당**: 정상·빈 결과·네트워크 오류·중복 선택·로그인 전후를 기기에서 점검합니다.
5. **통합 담당**: Fuseki 재적재가 필요한 변경인지 판별하고, API 스모크 테스트·비밀값 검사·변경 이력·`Backend` 푸시를 확인합니다.

## 4. 작업 카드 템플릿

각 작업은 PR 또는 작업 메시지에 아래 항목을 채웁니다.

```text
목표:
변경 범위(파일/API):
입력 데이터와 출처·라이선스:
완료 조건:
테스트 결과:
미결정 사항/다음 담당자:
푸시 커밋:
```
